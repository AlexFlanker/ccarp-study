D1 · 17%解决方案设计与架构

官方要求

业务问题→Claude方案翻译 · 端到端架构（输入→处理→输出→反馈环）· 架构模式选型（workflow / agentic / augmented LLM）· 多Agent编排 · 问题分解 · 业务价值对齐（效率/转型/生产力/成本/SLA）

考点 1 · 架构模式阶梯（最常考）

  • Augmented LLM：单次调用 + 检索 + 工具 + 记忆，一切设计的默认起点。
  • Workflow 五式（步骤可预知，用代码编排）：Prompt chaining（固定可分解步骤，级间可插校验门）；Routing(先分类再分发到专用提示/模型)；Parallelization（sectioning 切分并行 / voting 多次投票）；Orchestrator-workers（子任务动态、数量不可预知，由中心LLM拆解分发）；Evaluator-optimizer（有明确评价标准时生成↔评审迭代）。
  • Agent：开放式问题、步数不可预知、需依据环境反馈循环决策。代价：成本/延迟/不可控性上升，必须配护栏与停止条件。
口诀：能单次不链式，能链式不代理（agentic 是最后选项，不是最先）。选型题先问「步骤能不能提前写死」。

考点 2 · 分解与多Agent

  • 一个巨型 prompt 同时做抽取+校验+汇总而失败 → 拆成链式步骤、级间用结构化数据（JSON）传递，每步单独可测。
  • 多Agent：子代理在隔离上下文跑重活，只回传摘要（防主上下文污染，对应你模拟考 Q8 的 fork 思想）；编排者负责拆任务/汇总，worker 无共享状态时并行。
  • Worker 失败要有策略：部分结果可用 vs 全部重跑，考题常考「只重跑失败子任务」。

考点 3 · 业务价值对齐

  • 方案必须挂到可度量支柱：效率（省时）、成本、生产力、转型、性能 SLA。「先上AI再说」是错误选项的常见伪装。
  • 起步选窄而高频的工作流做试点，用基线数据证明价值，再扩面。

高频陷阱：①把 agent 当默认答案（过度工程）②反馈环缺失的「端到端」架构（人工纠错没有回流到评测集）③价值支柱写成空话没有度量。

D2 · 13%模型、提示与上下文工程

考点 1 · 模型选型三角（能力/成本/延迟）

  • 高吞吐、简单判定（分类/路由/子代理）→ 最小满足质量的模型（Haiku级）；生产主力均衡 → Sonnet级；深推理、低频高价值（法务/架构分析）→ 最强模型（Opus级）+ extended thinking。
  • 正确姿势：用评测证明小模型是否够用，混合路由（router 用小模型，难题升级大模型）。「无脑换最大/最小模型」几乎总是错误选项。

考点 2 · 提示工程武器库（对症下药）

症状处方
格式多样导致抽取失败Few-shot：2–4 个覆盖不同格式的示例（你的 Q14）；示例选边界样本而非堆数量
判断标准模糊、误报率高把形容词换成具体分类标准：明确标记什么/不标什么（你的 Q13）
模型缺领域隐性知识访谈模式让模型向专家提问再改写 prompt（你的 Q11）——加形容词/塞源码/加思考预算都补不了「没人告诉过它」的信息
多步推理错CoT / extended thinking（注意：只提升推理深度，变不出缺失的事实）
输出要严格 JSON结构化输出/prefill/工具调用 schema；temperature=0 只管一致性，不管理解

考点 3 · 上下文与缓存

  • Prompt caching：静态内容（tools→system→大文档）放前，动态用户消息放后，打缓存断点；前缀早段一改，之后全部失效。同降延迟+成本（官方样题2）。
  • 长上下文：大文档在前、问题在最后；先引用后回答（quote-first）提升 grounding。
  • 长会话：压缩/摘要旧轮次（compaction），外置记忆文件；别指望无限塞。
  • 复用策略：模块化提示、Skills 封装（按需加载，不占常驻上下文）。
口诀：静前动后打断点；示例治格式、标准治模糊、访谈治无知、思考治推理——先诊断缺什么，再选技术。
D3 · 19%集成：工具 / 认证 / RAG / 协议（权重最大）

考点 1 · 工具面设计（capability bloat）

  • 工具过多 → 选择准确率结构性下降：按任务模式作用域收窄，每次只暴露相关的 4–6 个（你的 Q3）；海量工具用渐进发现（tool search/按需加载定义）而非一次性全量灌入。
  • 描述要清晰、参数语义无重叠；「合并成大而全工具」仅当后端语义高度一致才对。
  • 最小权限：角色用不到的能力直接移除（官方样题1），日志/二次确认只是补偿控制，不等于消权。

考点 2 · 认证与授权

  • 识别缺口：共享服务账号 = 无法审计到人、权限过宽 → 按用户 OAuth、按工具最小 scope。
  • 反模式：token 透传（confused deputy）、密钥硬编码进版本库（你的 Q4：.mcp.json 入库 + 环境变量占位符）。
  • 多租户：检索层按租户做 metadata 过滤/索引隔离，权限在检索时生效而不是靠提示词。

考点 3 · RAG 管道（症状→处方）

症状最可能环节 / 处方
文档刷新后自信地答错检索/索引层坏了（重建索引、嵌入版本不一致）——官方样题3
检索到了但答不对chunk 太碎缺上下文 → 加大 chunk/overlap、parent-document、contextual retrieval（给块前置来源摘要）
主题相关但答非所问（precision 差）加 re-ranker，先召回后精排
查询词与文档术语不匹配 / 精确码号查不到query 改写扩展；hybrid（BM25+向量）——SKU/报错码/条款号必配关键词检索
要最新版本却检回旧文档metadata（版本/时间）过滤 + 时效加权
  • Chunking 选型：均质长文→固定大小+overlap；合同/代码/手册→按结构（条款/函数/标题）切；主题跳跃→语义切分。按数据形状和查询模式选，没有万能值。

考点 4 · 协议选型 + 错误设计

  • MCP：交互式助手、多工具动态发现、团队复用标准化；直接 API/CLI：固定单点调用、批处理管道、最低开销；Agent-to-Agent：跨团队/组织边界、各自独立演进，靠契约交互。
  • 工具错误返回结构化字段（errorCategory / isRetryable），让模型决定重试或终止（你的 Q2）；isError:false 掩盖失败是纯反模式。
  • 需要强制调用：tool_choice: any（必须调用但自选哪个，你的 Q15）；tool 强制指定；提示词「必须调用」是软约束，不如 API 硬约束。
  • 观测规模化：结构化事件 + trace ID 贯穿工具调用链 + 抽样审查转录，而非人肉看全量日志。
  • 精度-延迟权衡：确定瓶颈环节再动手（缓存高频查询、异步预计算、小模型精排），并能向干系人论证取舍。
口诀：用不到就删（最小权限）、選不准就减（作用域收窄）、查不准先分症状（索引/召回/精排/术语/时效五问）、错误要结构化、强制调用用 any。
D4 · 16%评测、测试与优化

考点 1 · 评测体系设计

  • 顺序铁律：先建评测集，再调 prompt。评测集来源：真实失败案例 + 人工金标 + 边界样本；持续把线上纠错回流进来。
  • 三类打分器混用：code-graded（格式合法、schema 符合、可执行——能用代码判就用代码）；LLM-as-judge（主观质量：给锚定量表 rubric + 人工抽检校准 + 防位置/自恋偏好）；human（金标准，贵，用于校准前两者）。
  • 指标全家桶：accuracy / latency(p50与p95分开) / cost / safety / security，别只报一个。

考点 2 · 诊断分诊（哪层坏了）

  • 幻觉引用不存在的内部API → 缺 grounding（给检索/文档），不是调 temperature。
  • 改了 prompt 后整体变差 → 缺回归评测门禁；A/B 要样本量+显著性，canary 灰度 + 自动回滚阈值。
  • 校验重试循环失败率恒定不降 → 先分类失败原因：数据缺失类（输入里根本没有）重试无用，要补充信息或转人工（你的 Q16）；理解偏差类才值得带反馈重试。
  • 自查抓不住错 → 独立审查：新实例、只给源文档+结果、不带生成方对话历史（你的 Q18，锚定偏差）。

考点 3 · 成本与延迟优化

  • 输入大头是重复前缀 → prompt caching；离线大批量 → Batch API（半价、24h窗口、custom_id 定位失败、只重交失败项+超长文档先切分，你的 Q17）。
  • 延迟：流式输出、小模型先答+难题升级、并行化工具调用；成本归因到 feature/租户级别才能治理。
  • 观测：记录 prompt/completion（PII 脱敏）+ token/成本/延迟指标 + trace 关联，仪表盘看趋势。
口诀：没有评测集就没有优化；能代码判不用模型判；自查不可信，独立才可信；重试前先问「失败是不知道，还是做不对」。
D5 · 14%治理、安全与风险管理

考点 1 · 护栏与失效模式

  • 分层防御：输入过滤/分类器 → 系统提示约束 → 工具白名单+最小权限 → 输出审查 → 审计日志。只靠「在系统提示里恳求」是软约束，单层必挂。
  • Prompt injection（必考）：直接注入 vs 间接注入（检索文档/网页/邮件内容里藏指令）。处方：外部内容当数据不当指令（隔离标记）、检索后限制高危工具、敏感动作出站白名单——邮件Agent被邮件正文指挥外发数据是经典场景。
  • 失效模式清单：幻觉、过度代理（excessive agency：给了生产删除权）、数据外泄（通过工具出站）、越权、级联失败。控制爆炸半径：沙箱、dry-run、配额。

考点 2 · Human-in-the-loop

  • 不可逆/高价值动作（退款、删号、对外发送）设审批门 + 审计留痕；低风险自动放行。
  • 审批疲劳 → 风险分级：高危全审、中危抽检、低危事后审计，别把人变橡皮图章。

考点 3 · 合规映射

法规考点触发词架构含义
GDPR欧盟个人数据、删除权、数据驻留数据最小化；被遗忘权要能删到向量库和日志；区域驻留/子处理方合规；目的限定
HIPAAPHI、医疗BAA 协议、传输/存储加密、脱敏后再进模型、零保留配置、访问审计
FedRAMP美政府、联邦机构只能部署在授权边界内（Gov 云类环境），消费级端点直接排除

考点 4 · 伦理 AI

  • 招聘/信贷类：跨群体公平性评测 + 人做最终决定 + 可解释（引用依据）；对终端用户披露 AI 生成；上线前红队测试；留事故响应预案。
口诀：外来内容皆数据；不可逆必过人；删除权删到向量库；医疗签BAA、政府进边界；单层护栏=没有护栏。
D6 · 14%干系人沟通与生命周期管理

考点 1 · 结构化发现（discovery）

  • 高管说「给我们上AI」→ 先结构化访谈挖业务问题与成功指标，再谈技术；先问量级/延迟SLA/合规约束等非功能需求，后选模型。凡是「直接开始搭」的选项都错。
  • 成功标准要可量化且提前书面对齐（如：deflection rate ≥30%，p95 ≤3s，幻觉率 <2%）。

考点 2 · 决策沟通与期望管理

  • ADR（架构决策记录）：背景 + 备选方案 + 取舍 + 后果，让决策可追溯——对 CTO 讲 trade-off 而不是结论。
  • 干系人期望 100% 准确 → 对齐错误预算：LLM 是概率系统，尾部风险用 HITL 兜底；演示 ≠ 生产，pilot 数据说话，别拿樱桃采摘的 demo 承诺。
  • SLA：定义 p95 延迟 + 降级路径（缓存答案/转人工/小模型兜底），提前沟通降级预案。

考点 3 · 生命周期与交接

  • 阶段：发现 → 设计 → 交付/handoff → 监控 → 迭代。每阶段有产出物。
  • Handoff 包：runbook、prompt 注册表（版本化）、评测面板、告警阈值、升级路径；知识转移要验证（shadow 轮值、演练），不是发个文档完事。
  • 反馈闭环：pilot 用户纠错 → 定期分诊 → 进评测集 → 改进 → 向干系人回报——闭环要能画出来。
口诀：先指标后技术；讲取舍不讲结论；期望管理=错误预算；交接看 runbook，闭环看回流。

大库检索追踪重命名/桥接：先读桥接文件拿全别名，再按别名精确检索；避免全目录通读或通用词全文搜Q5
  • 团队级配置治理：权限基线（allowed tools 策略）、共享 hooks 做危险命令门禁、入职即用的仓库内配置。
  • 运维支援：用日志/转录定位是 prompt、工具还是环境问题——分层排查思路与 D4 相通。
口诀：团队的进仓库，个人的留本机；密钥进 env；吵的 fork 出去；没人看的用 -p，要人审的开 plan。

错误选项四大特征（做题元技能）

  • 虚构机制：不存在的参数/配置（如 --batch、CLAUDE_HEADLESS、按 .mcp.json 顺序路由）→ 见到秒排除。
  • 治标不治本：只处理症状（加重试、加日志、加阈值告警）而不动根因 → 题干问 best/root cause 时排除。
  • 反模式：违背协议语义或安全原则（isError:false、token 透传、密钥入库、自动批准的审批）。
  • 过度工程：规模不匹配的重型方案（为 3 个工具建路由层、为小项目上多Agent）。

官方样题（Exam Guide §8 原题）

样题 1 · D3 集成

客服 Agent 能读工单、拟回复、退款、删除账户；客服只需要前两项。按最小权限，哪项最能降险？

  • A. 给退款/删除工具加日志便于事后审计
  • B. ✔ 从配置中彻底移除退款与删除工具
  • C. 保留全部工具但退款/删除前加确认
  • D. 换更大的模型以更可靠地遵循指令

最小权限=移除不需要的能力、消灭攻击面。日志(A)/确认(C)是侦测/补偿控制；模型大小(D)与授权范围无关。

样题 2 · D2 模型与提示

每次请求都发相同的 8000-token 系统提示+政策文档，后跟很短的动态用户消息；延迟和成本都要优化。选哪个？

  • A. 政策文档截断到前1000 token
  • B. 无视任务契合度换最小模型
  • C. ✔ 静态内容前置 + 开启 prompt caching
  • D. 把政策文档挪进 few-shot 示例块

稳定前缀可复用缓存，同降 TTFT 和单价且不丢上下文。截断丢政策；盲目降级伤质量；挪进few-shot不构成可缓存前缀。

样题 3 · D4 评测

RAG 在文档刷新后开始自信地答错，延迟与模型版本未变。先查哪里？

  • A. 模型权重被悄悄改了
  • B. ✔ 检索/索引环节返回了不相关或过期的 chunk
  • C. temperature 太低
  • D. 上下文窗口缩水了

「文档刷新」是唯一变量→指向索引/嵌入管道故障，其余选项与该触发事件无因果。

D1 端到端架构D2 缓存/长上下文D3 RAG全链路D4 评测观测

场景

把一批内部文档（可用任意开源手册/政策文集模拟，含表格与多版本文件）做成可溯源问答服务：答案必须带引用，回答不了要明说。

步骤

设计文档：画输入→检索→生成→反馈环的端到端架构图，写清非功能需求（延迟/成本/更新频率）——练 D1/D6

生成侧：静态系统提示+政策前置并开 prompt caching；要求 quote-first 引用；答不了就拒答
建 30–50 条评测集（含「答案不在库里」的陷阱题）：retrieval 命中率与 faithfulness 分开测
故障演练：故意换 embedding 模型不重建索引、故意灌入一条带注入指令的文档，观察并修复——复现官方样题3与间接注入
加日志：query/检索结果/答案/token成本 trace 关联，做一页监控面板
验收：检索命中率 ≥85%；faithfulness 评测 ≥90%；陷阱题拒答率 100%；能演示「文档刷新后质量下降→定位到索引」的完整排障过程。
